Reinforcement Learning Search and Rescue Robot

June 2026 – August 2026

C++ • Python • ROS 2 • Isaac ROS • Reinforcement Learning • NVIDIA Jetson • cuVSLAM • NVBlox • YOLOv8 • TensorRT • Nav2

Building a Robot That Decides Where to Search

This project began with a simple question: if a mobile robot is looking for an object somewhere inside an apartment, how should it decide where to search next?

Getting a robot to drive to a known destination is already a substantial robotics problem. The robot must estimate its position, understand the geometry of the environment, plan a collision-free path, execute that path, and interpret camera observations along the way. Object search adds another layer: the destination is not known in advance.

I built an autonomous mobile robot around an NVIDIA Jetson Orin Nano and an Intel RealSense D435I. The final system combined visual SLAM, 3D mapping, Nav2 navigation, YOLO-based object detection, Bayesian belief updates, and a reinforcement learning policy that selected which region of the apartment the robot should inspect next.

Rather than replacing the entire robotics stack with a learned policy, I used reinforcement learning only for the part of the problem where learning was useful: high-level search strategy. Classical robotics components remained responsible for localization, mapping, path planning, obstacle avoidance, and low-level motion.

Connecting the Physical Robot to ROS 2

Before the robot could search autonomously, the hardware first needed to behave like a normal ROS 2 mobile base.

The Jetson Orin Nano acted as the onboard computer and ran Ubuntu 22.04 with ROS 2 Humble. An Intel RealSense D435I provided stereo infrared images, RGB images, depth measurements, and inertial data. A separate motor controller drove the mobile base over a serial connection.

ROS 2 components communicate by publishing and subscribing to named topics. This makes the individual subsystems largely independent. A navigation algorithm does not need to know which motor controller is installed on the robot; it only needs to publish the appropriate velocity command.

Nav2 outputs velocity commands using the standard ROS 2 /cmd_vel interface. I created a bridge between these velocity commands and the serial protocol understood by the motor controller. The bridge converted desired linear and angular velocities into physical drive commands transmitted through /dev/ttyACM0.

This abstraction became important later in the project. The navigation stack, search policy, and perception system could all operate using standard ROS interfaces without being tightly coupled to the particular chassis underneath them.

Defining Where Everything Is: The ROS Transform Tree

Once the base could move, the next problem was establishing a consistent spatial coordinate system.

A robot rarely operates in only one coordinate frame. The camera measures objects relative to itself, the robot moves relative to its base, odometry describes local motion, and a map describes positions in the global environment.

ROS 2 handles these relationships using the TF transform system. Every sensor and coordinate frame forms part of a transform tree that allows a point measured in one frame to be expressed in another.

The final transform structure used by the robot was: 

map
└── odom
    └── base_link
        └── camera0_link

Here, map represents the global apartment map, odom tracks locally continuous robot motion, base_link represents the robot chassis, and camera0_link represents the mounted RealSense camera.

The camera transform was defined from the measured physical mounting position on the robot. Establishing this transform correctly was essential because errors in the camera pose propagate directly into visual localization, 3D mapping, and obstacle geometry.

Localizing the Robot with Visual SLAM

Autonomous navigation requires the robot to continuously answer two questions: where am I? and what does the environment around me look like?

I used NVIDIA Isaac ROS Visual SLAM with cuVSLAM to estimate the motion of the robot from the RealSense stereo cameras. The left and right infrared image streams provided synchronized stereo observations that could be used to track visual features and estimate camera motion over time.

Visual SLAM differs from simple wheel odometry because it estimates motion by observing how features in the environment move between camera frames. This was particularly useful for the platform because it provided localization without requiring a dedicated 2D LiDAR.

cuVSLAM published the transformations needed to connect map, odom, and base_link. Once this portion of the stack was stable, the robot could be driven around the apartment while maintaining a continuously updated estimate of its position.

Turning Camera Data into a 3D Map

Localization alone tells the robot where it is, but navigation also requires a model of the surrounding geometry.

I integrated NVBlox, NVIDIA's GPU-accelerated mapping system, with the RealSense depth stream and cuVSLAM poses. NVBlox incrementally fused depth measurements as the robot moved through the apartment, producing a volumetric representation of the environment.

Instead of treating every camera frame independently, volumetric mapping integrates many observations into a shared world model. Surfaces observed repeatedly from different viewpoints become part of the same reconstructed geometry.

The mapping pipeline produced both a 3D mesh and an ESDF representation. An Euclidean Signed Distance Field, or ESDF, stores the distance from locations in space to the nearest obstacle. This representation is especially useful for collision-aware planning because it provides more information than a binary occupied/free map.

For this robot, NVBlox used 10 cm voxels and integrated depth measurements out to approximately 5 meters. The reconstructed apartment could then be exported as a 3D mesh and converted into the 2D representation needed by Nav2.

From a 3D Reconstruction to a Navigation Map

The perception stack produced a rich 3D representation, but the mobile robot itself primarily moved across a 2D floor plane. For navigation, I therefore extracted a horizontal collision representation from the reconstructed environment.

The resulting occupancy map represented the apartment as a grid in which each cell described navigable space, an obstacle, or an unknown region. The final map used a resolution of approximately 7.5 cm per cell.

This map became the shared spatial reference for the remainder of the project. Navigation goals, search locations, object observations, and the robot's position could now all be expressed in the same global coordinate system.

Autonomous Navigation with Nav2

Once the robot had a map and a reliable localization estimate, I integrated Nav2 to move between arbitrary positions in the apartment.

Nav2 separates navigation into several related problems. A global planner finds a route through the known map, a local controller continuously produces motion commands, and local costmaps represent nearby obstacles that must be avoided while the robot follows the route.

The global planner operated in the map coordinate frame while the rolling local costmap operated in odom. The local map covered a region surrounding the robot and continuously moved with it. Inflation around detected obstacles prevented the planner from selecting paths that passed too close to walls or furniture.

After tuning the robot footprint, velocity limits, inflation parameters, and controller behavior, the system successfully executed complete NavigateToPose actions in the mapped apartment.

At this point, the robot could autonomously travel to a known destination. That changed the original object-search problem significantly: instead of asking a learning algorithm to control the motors directly, I could ask it a much simpler high-level question:

Which destination should Nav2 visit next?

Giving the Robot Semantic Perception

Geometry tells the robot where walls and obstacles are, but it does not tell the robot what it is looking at. Search requires semantic information.

I added a YOLOv8 perception pipeline using the RealSense RGB stream. Camera frames were passed through a TensorRT-optimized detector running on the Jetson, producing object classes, confidence scores, and bounding boxes.

The perception stack published detections through ROS 2 so that the search controller did not need to know anything about the underlying neural network implementation. After filtering and confirmation, observations relevant to the search problem were exposed through: 

/confirmed_search_detections

This interface separated visual perception from decision making. YOLO answered the question what objects can I currently see?, while the search policy answered where should I go next?

Representing the Apartment as Search Locations

With reliable navigation and perception working independently, the remaining problem was deciding how the robot should search.

Allowing the policy to choose arbitrary coordinates would have created a very large and unnecessarily difficult action space. Instead, I represented the apartment using a set of strategically selected vantage points.

Each vantage point corresponded to a position from which the camera could inspect an important region of the apartment: areas around the desk, beds, entrance, living room, kitchen, and other locations where the target might plausibly appear.

The search policy selected between ten possible locations: 

desk_entry
desk_middle
desk_deep
left_bed_entry
left_bed_deep
entrance
living_room
front_bed
kitchen
right_bed

After a location was chosen, Nav2 handled the details of reaching it. This created a useful hierarchy: 

Reinforcement Learning
        ↓
Choose next search location
        ↓
Nav2
        ↓
Plan and execute collision-free path
        ↓
YOLO
        ↓
Observe objects at destination

The learned policy therefore operated at the level of decision making, not low-level control.

Using Objects as Clues

A purely geometric search strategy might simply visit the nearest unexplored location. However, indoor environments contain semantic structure. Objects often provide information about where other objects are likely to be located.

For example, observing a keyboard provides evidence that the robot is near a desk. A backpack, bowl, or other contextual object can similarly provide clues about which region of the apartment the robot is currently observing and how likely the target is to appear nearby.

I represented this information using Bayesian belief updates. As the robot collected observations, the probability assigned to different search regions could change instead of remaining fixed throughout the episode.

Six clue observations were incorporated into the search environment: 

backpack_desk
backpack_entrance
backpack_front_bed
bowl_front_bed
hair_drier_left_bed
keyboard_desk

Combining these observations with reinforcement learning allowed the policy to make decisions based on both travel cost and information gathered so far.

Building the Search Problem as a Gymnasium Environment

I implemented the high-level decision problem as a custom Gymnasium environment so that search strategies could be trained and evaluated independently from the physical robot.

The action space was discrete: each action selected one of the ten search vantage points.

The observation included the robot's current search location, which locations had already been visited, confidence values associated with semantic clues, and the amount of search time remaining. The final state representation contained 38 values.

Each episode was also constrained by a time budget. I evaluated search behavior under budgets of 30, 60, 120, and 300 seconds. Moving between vantage points incurred time based on travel distance together with an observation overhead.

The episode terminated when the target was found or when the available search time expired.

Preventing Impossible Decisions with Action Masking

Standard reinforcement learning policies assign probabilities to every action in the action space. But in this environment, some actions should not be available at a particular moment.

For example, repeatedly selecting a vantage point that had already been searched generally provides little useful information. An action may also be infeasible if the remaining time budget is too small to reach that location.

I therefore used action masking to explicitly mark unavailable actions before the policy selected its next destination.

This reduces wasted exploration during training and makes the policy's action space better reflect the actual state of the search problem.

Training the Search Policy with Maskable PPO

The search policy was trained using Maskable Proximal Policy Optimization (Maskable PPO).

PPO is a policy-gradient reinforcement learning algorithm. The policy receives the current search state and produces a probability distribution over possible destinations. During training, that distribution is gradually adjusted toward decisions that produce greater expected reward.

The reward function strongly rewarded successful target discovery while penalizing timeout and invalid behavior. The objective was not simply to maximize the probability of eventually finding the object; the policy needed to find it while using the available search time efficiently.

I trained the Maskable PPO policy for approximately one million environment steps before evaluating it against several non-learning baselines.

What Should Reinforcement Learning Beat?

Reinforcement learning is only useful if it improves on simpler decision rules. I therefore implemented multiple baseline strategies rather than evaluating the learned policy in isolation.

The baselines included a nearest-unexplored strategy, a probability-greedy strategy, and a posterior-greedy strategy. These methods captured reasonable alternatives such as always choosing the closest unvisited location or always selecting the location currently believed most likely to contain the target.

The difference is that the learned policy could optimize decisions over the entire remaining search horizon rather than optimizing only the immediate next move.

Connecting the Learned Policy Back to the Robot

Training the search policy in a Gymnasium environment was only useful if its decisions could be executed by the real robot.

I built a search controller that connected the abstract RL environment to ROS 2. Each high-level action was translated into a physical pose in the apartment and sent to Nav2 as a navigation goal.

Once the robot reached the requested vantage point, the controller collected confirmed YOLO observations, updated the search state, and requested another action from the policy.

Conceptually, the deployed loop became: 

Policy selects vantage point
        ↓
Send NavigateToPose goal
        ↓
Nav2 drives robot to destination
        ↓
Camera observes environment
        ↓
YOLO detects semantic clues / target
        ↓
Update Bayesian belief
        ↓
Policy selects next vantage point

This continued until the target was detected or the search budget expired.

Evaluating Search Efficiency

I evaluated the learned policy across 10,000 randomized search episodes and compared its performance with the greedy baselines.

Randomization changed the conditions of the search rather than measuring performance on a single fixed scenario. This allowed the evaluation to test whether the policy had learned a useful search strategy rather than memorizing one particular route.

Across the evaluation set, the reinforcement learning policy reduced average search time by approximately 13% compared with the greedy baseline.

The result was particularly important because reinforcement learning was not being used simply to demonstrate that a robot could move. The classical robotics stack already handled that. The improvement came specifically from learning how to allocate the robot's search time.

The Final Autonomy Stack

By the end of the project, the robot combined several independently complex systems into one autonomy pipeline: 

Intel RealSense D435I
        ↓
Isaac ROS Visual SLAM / cuVSLAM
        ↓
Robot localization
        ↓
NVBlox
        ↓
3D reconstruction + navigation map
        ↓
Nav2
        ↓
Autonomous motion between search locations

RealSense RGB Camera
        ↓
YOLOv8 + TensorRT
        ↓
Confirmed semantic detections
        ↓
Bayesian belief update
        ↓
Maskable PPO search policy
        ↓
Next search location
        ↓
Nav2

This architecture deliberately separated perception, localization, navigation, and decision making. Each subsystem had a clear interface, which made the complete robot substantially easier to debug and improve.

What I Learned

The most important lesson from this project was that applying machine learning to robotics does not necessarily mean replacing the entire autonomy stack with a neural network.

Visual SLAM was already well suited for estimating motion. NVBlox was well suited for geometric mapping. Nav2 was well suited for collision-aware navigation. YOLO was well suited for semantic perception. Reinforcement learning became useful only after these components transformed the original robotics problem into a compact decision problem: choosing the next place to search.

Building the complete system also exposed the integration work that is often hidden when robotics algorithms are studied independently. Coordinate frames, camera calibration, topic interfaces, map representations, navigation tuning, inference latency, physical motion, and failure handling all had to work together before improvements in the search policy mattered.

The final robot demonstrated an end-to-end autonomy pipeline running onboard an NVIDIA Jetson: perceive the environment, localize within it, construct a map, navigate through it, interpret semantic observations, update beliefs, and learn where to search next.

Future Improvements

The current system represents the apartment using a fixed set of discrete vantage points. A natural extension would allow the robot to generate new observation poses dynamically based on uncertainty, visibility, and expected information gain.

The semantic belief model could also be expanded beyond a small set of manually defined clue relationships. Learned scene representations or object co-occurrence models could provide richer priors about where an unseen target is likely to appear.

Finally, search could be extended from a single known apartment to previously unseen environments, where mapping, exploration, semantic reasoning, and target search would need to occur simultaneously.
