Building a Real-Time Physiological Monitor

The goal of this project was to build an embedded physiological monitoring system capable of measuring an ECG signal, estimating heart rate, reading temperature, monitoring battery state, and communicating the results over Bluetooth Low Energy.

Individually, none of these tasks is especially complicated. The interesting problem appears when they all have to run on the same microcontroller. ECG acquisition requires consistent timing, battery measurements should happen periodically, Bluetooth events arrive asynchronously, and user inputs can occur at any point in execution.

The project therefore became less about interfacing with individual sensors and more about designing a small real-time system that could coordinate several independent pieces of hardware predictably.

Step 1: Defining How the Device Should Behave

Before implementing the individual sensors, I first needed a clear model for how the device should behave. Allowing every peripheral to independently change system behavior would quickly make the firmware difficult to reason about.

I therefore organized the application as a finite-state machine with five primary states: INIT, IDLE, BATTERY, MEASURE, and ERROR.

A state machine represents a system as a finite set of operating modes with explicit transitions between them. At any point in time, the firmware knows what state it is in and therefore which operations are valid.

For this device, INIT performs hardware setup before transitioning to IDLE. From IDLE, an event can start a physiological measurement or a periodic battery measurement. When either operation completes, the system returns to IDLE. Any serious failure redirects execution into ERROR.

This structure became the backbone of the firmware. The remaining embedded-system concepts were introduced as the implementation required mechanisms for timing, concurrency, hardware input, and communication.

Step 2: Moving from a Main Loop to an RTOS

A simple embedded program can often run inside one infinite loop: read an input, perform some work, update an output, and repeat. That approach becomes harder to maintain once several operations have different timing requirements or can occur asynchronously.

Our monitor had exactly that problem. A 30-second ECG measurement should not prevent the system from managing timing or asynchronous hardware events, and periodic battery monitoring should not require blocking the processor until the next measurement is due.

I used Zephyr RTOS to provide the scheduling and synchronization infrastructure for the firmware.

A real-time operating system provides abstractions such as threads, timers, events, and work queues on top of a small kernel. The kernel manages when executable work runs and allows independent pieces of firmware to coordinate without manually building an entire scheduler inside the application.

The important distinction is that Zephyr did not replace the state machine. The state machine defined what the device should do, while the RTOS provided the mechanisms for deciding when different pieces of work could run.

Step 3: Giving the Control Logic Its Own Thread

Once the system became event driven, the main control logic needed a way to wait for new work without continuously polling every peripheral. This is where a thread became useful.

A thread is an independently schedulable sequence of execution. On a single-core microcontroller, multiple threads are not generally executing instructions at exactly the same instant. Instead, the RTOS kernel switches between runnable threads according to their state and priority.

The system control logic can therefore wait for an event rather than constantly consuming processor time. When there is nothing to do, the thread blocks. When a measurement request, battery timer, or error event arrives, the kernel wakes the appropriate execution path and the state machine responds.

This was useful because the control flow did not need to manually poll for every possible condition. The application could remain idle until something meaningful actually happened.

Step 4: Turning Hardware Activity into Events

The next problem was asynchronous input. A user might request a measurement at any time, a timer might expire, or a peripheral operation might fail.

Continuously checking for these conditions would waste processor time, so the firmware uses an event-driven approach.

A kernel event is a synchronization mechanism that allows one part of the firmware to signal that something has happened. Another execution context can wait for that event and continue only when the corresponding event bit is posted.

In this project, events connect asynchronous activity to the state machine. A measurement request can generate an event that moves the system from IDLE to MEASURE, while a detected fault can generate an error event that redirects execution into ERROR.

Hardware inputs also introduce the idea of an interrupt. An interrupt allows hardware to notify the processor that something happened instead of forcing software to poll the hardware repeatedly.

The interrupt-side work is intentionally kept small. Rather than doing an entire ECG measurement or state transition inside an interrupt handler, the asynchronous input is converted into an event and the larger operation is handled by normal RTOS-managed code.

This separation keeps interrupt handling fast while keeping the actual application behavior inside the state machine.

Step 5: Scheduling Periodic Work with Timers

Some operations were not triggered by a user at all. Battery state, for example, should be checked periodically while the device continues doing other work.

A naive implementation could call a delay function and wait for the required interval. The problem is that a blocking delay prevents that execution context from doing useful work during the wait.

An RTOS timer solves this by allowing the kernel to track elapsed time independently. The application can schedule an operation for the future and continue executing other work while the timer runs.

The battery-monitoring path uses this idea to trigger periodic measurements while the system is otherwise idle. When the timer expires, it signals that battery work is ready rather than requiring the firmware to spend an entire minute counting time inside the main control flow.

Timers are also useful for periodic device behavior such as status LEDs, where precise repeated timing is needed without filling the program with blocking delay loops.

Step 6: Acquiring an Analog ECG Signal

With the control architecture in place, the next step was implementing the primary measurement path: ECG acquisition.

An ECG is an analog voltage waveform, while the microcontroller operates on digital values. The bridge between these two domains is the analog-to-digital converter, or ADC.

An ADC periodically samples an input voltage and converts it into a numerical representation. For an ECG signal, a single sample is not particularly useful; the shape and timing of many consecutive samples contain the physiological information.

When the state machine enters MEASURE, the firmware acquires ECG samples across an approximately 30-second measurement window. Maintaining consistent sampling behavior is important because the heart-rate calculation depends on the timing between repeated cardiac cycles.

The firmware then analyzes the sampled waveform and converts the repeated beats into an average heart rate in beats per minute.

Step 7: Processing the ECG on the Microcontroller

The sampled ECG contains repeating cardiac cycles. By identifying the timing of successive beats, the firmware can calculate how frequently they occur and convert that interval into BPM.

Performing this processing directly on the embedded target means the external device does not need the raw ECG waveform simply to determine heart rate. The microcontroller acquires the signal, extracts the measurement, and exposes the resulting BPM.

I validated the complete path using known reference heart rates and compared them with the values produced by the embedded system and transmitted over Bluetooth.

Step 8: Adding a Digital Temperature Sensor

Temperature required a different type of sensor interface. Unlike the ECG signal, the MCP9808 temperature sensor performs its own analog-to-digital conversion internally.

The microcontroller therefore communicates with the sensor using I²C, a synchronous serial bus commonly used for low-speed embedded peripherals. I²C uses shared clock and data lines, with device addresses allowing multiple peripherals to communicate over the same bus.

During the MEASURE state, the firmware communicates with the MCP9808 over I²C, retrieves the temperature measurement, and stores it alongside the calculated heart rate.

This gave the project two fundamentally different sensing paths: continuous analog acquisition for ECG and register-based digital communication for temperature.

Conceptually:

ECG → ADC → Sampled Waveform → Heart-Rate Processing

while:

MCP9808 → I²C → Digital Temperature Measurement

Step 9: Getting the Measurements Off the Device

Once the monitor could calculate heart rate and measure temperature, those values needed a way to reach an external device.

I used Bluetooth Low Energy, or BLE, because it is designed for low-power communication between embedded peripherals and nearby devices such as phones and computers.

BLE organizes application data through the Generic Attribute Profile, or GATT. Instead of sending an arbitrary stream of bytes, data is organized into services and characteristics with defined meanings.

The monitor operates as a BLE peripheral. Heart rate is exposed through the standard Heart Rate Service, battery information through the Battery Service, and device metadata through the Device Information Service.

Temperature and firmware error information are exposed using custom characteristics because they do not fit the same standard service structure used elsewhere in the device.

BLE notifications are sent after new measurements have been processed. Notifications are useful because the peripheral can push a new value to a connected client instead of requiring the client to repeatedly poll for changes.

At this point, the complete physiological pipeline became:

Sensor → Peripheral Interface → Embedded Processing → GATT Characteristic → BLE Client

Step 10: Adding Background Battery Monitoring

Physiological measurement was not the only information the device needed to manage. The firmware also periodically monitors an analog battery signal through another ADC input.

This path demonstrates why the earlier timer and state-machine architecture are useful. Battery measurement does not need to run continuously, and it should not interfere with an active ECG measurement.

Instead, the RTOS timer indicates when a battery measurement is due. If the system is available, the state machine enters BATTERY, acquires the ADC measurement, processes the result, and then returns to IDLE.

The resulting battery value is then used in three independent output paths: internal firmware reporting, Bluetooth's Battery Service, and a local LED indicator.

Step 11: Converting Software State into Physical Feedback

Not every output needed to go through Bluetooth. LEDs provide an immediate way to communicate device state without requiring a connected client.

Battery level presented an interesting problem because it is a continuous value rather than a simple on/off condition. To represent that value physically, the firmware uses pulse-width modulation, or PWM.

PWM rapidly switches a digital output between high and low states. Changing the percentage of each cycle spent in the high state—the duty cycle—changes the average power delivered to the LED and therefore its apparent brightness.

The battery measurement is mapped to PWM duty cycle so LED brightness changes with battery level. This creates a direct path from an ADC measurement through firmware processing to a physical hardware output.

Heart rate is also reflected through timed LED behavior after a completed measurement, allowing a processed physiological value to be represented physically as well as through Bluetooth.

Step 12: Designing the System for Failure

Once multiple peripherals were involved, assuming every hardware operation would succeed was no longer reasonable. ADC configuration, sensor communication, Bluetooth operations, and initialization can all fail.

This is why ERROR was designed as a first-class state rather than as a collection of scattered error messages.

When a subsystem detects a serious failure, it posts an error event. The state machine can then transition into ERROR from a known point in the control flow.

Normal device behavior is stopped, the error condition is recorded, and the system provides a clear fault indication. Error information can also be exposed to a BLE client through the custom error characteristic.

Recovery is explicit rather than accidental. A reset action returns the application from ERROR to a known operating state instead of attempting to continue after an unknown partial failure.

This is another place where the state-machine architecture helped: failure behavior became deterministic and visible rather than being hidden inside individual peripheral functions.

Step 13: Validating Complete Data Paths

Testing individual functions is useful, but an embedded system can fail at the boundaries between those functions. For that reason, I focused on validating complete signal paths through the device.

For heart rate, known reference inputs were passed through ECG acquisition, embedded processing, and Bluetooth transmission before the final reported BPM was compared with the reference.

Battery testing followed the same idea. A known analog input traveled through the ADC and firmware before being observed through internal logging, PWM output, and Bluetooth.

The goal was therefore not simply to verify that the ADC worked or that Bluetooth worked independently. It was to verify chains such as:

Physical Input → Peripheral → Firmware → Processing → Communication / Hardware Output

That end-to-end testing was especially valuable because it exposed the interactions between the different layers of the embedded system.

Putting the System Together

What began as several separate sensing and communication requirements ultimately became a small real-time software architecture.

The state machine gave the application predictable high-level behavior. Zephyr's kernel provided the underlying scheduling and synchronization mechanisms. A thread allowed control logic to wait for work rather than continuously polling, kernel events connected asynchronous activity to the state machine, and timers scheduled periodic operations without blocking execution.

At the hardware boundary, ADCs converted analog ECG and battery signals into digital measurements, I²C connected the digital temperature sensor, and PWM translated processed values back into physical output. BLE then provided a structured wireless interface between the embedded system and an external client.

The completed architecture can be summarized as:

Hardware Events / Sensors → Peripheral Drivers → RTOS Kernel → Events & State Machine → Processing → BLE / Physical Output

The most valuable part of the project was learning how these embedded concepts fit together. Threads, timers, interrupts, events, ADCs, I²C, PWM, and Bluetooth are not isolated features; each solves a particular problem that appears while building a responsive real-time system.
